# 可实施需求写法

## 单条需求结构

使用以下顺序组织：角色与场景 → 前置条件 → 触发动作 → 系统行为 → 业务规则 → 输入与输出 → 权限和留痕 → 异常处理 → 验收标准 → 来源和推导说明。

推荐句式：

> 当【场景】发生且满足【前置条件】时，具有【角色】权限的用户可以【动作】；系统应按照【规则】处理【输入】，生成【输出】，并在【异常】时给出【处理结果】。验收时通过【验证方法】确认【可观察结果】。

## 原文转需求

先保留原文，再拆分多个原子需求。不要把“建设综合平台、实现统一管理、提升服务能力”直接当成一个功能；应分别分析目标、对象、流程、数据、权限、指标和验收依据。推导需求要写明“为实现哪条原文要求，因此需要哪项能力”。

## 验收标准

验收标准优先采用可观察结果：页面操作结果、状态变化、字段校验、权限差异、接口报文、数据统计口径、日志记录、响应时间、并发量、容灾切换、导入导出结果或文档交付物。避免只写“功能正常”“满足要求”“用户体验良好”。

## 模糊词处理

发现实时、稳定、便捷、智能、统一、自动、灵活、可视化等词时，追问对象、范围、时限、指标、角色、数据来源和验证方法。若资料没有依据，不擅自填写数值，写入待确认清单并提供可选指标口径。

## 优先级

建议采用：`MUST`（合同、政策、验收或核心流程必须满足）、`SHOULD`（重要但可通过评审调整）、`COULD`（优化或先进能力）、`TBD`（资料不足，待决策）。优先级必须说明依据，不以“看起来重要”代替理由。
